# Security Design

## Identity and access

| Control | Implementation |
|---|---|
| Credentials | The Auth Lambda stores only a PBKDF2-SHA256 hash (210,000 iterations, random salt) in a separate `EMAIL#<email>` item of the Users table; the hash is never returned by the API and passwords are never logged. Wrong password and unknown email give the same 401 in the same time. Password policy: ≥ 8 chars, upper, lower, number. |
| Token validation | **Lambda Authorizer** on every protected route: HS256 signature (constant-time compare, `alg` must be HS256), issuer `<project>-<env>`, `token_use = access`, expiry. Missing header → 401, rejected token → 403, both before any Lambda runs. Refresh tokens are accepted only by `/auth/refresh`. The signing key (`random_password.jwt_secret`) is given only to the Auth and Authorizer functions. |
| Roles | `role` (`customer` / `admin`) stored on the user profile, copied into the access token at login and passed on by the authorizer. Every admin handler calls `require_admin` → 403. Roles in request bodies are ignored (unknown fields are rejected). Admins are created only with `scripts/create-admin.sh` (writes the Users table with lab credentials); self-registration always yields a customer. |
| Ownership | `GET /orders/{id}` returns 404 unless `order.customerId == token.sub` (or admin). Lists are queried by the caller's `sub`, and pagination tokens for another customer are rejected. |
| Token lifetime | Access/ID 60 min, refresh 1 day, revocation enabled, `prevent_user_existence_errors`. |
| Browser storage | Access token in memory + `sessionStorage` (tab-scoped); refresh token in memory only; never `localStorage`. Assessment: an XSS bug could still read the access token for ≤ 60 min, so the app renders no HTML from data (React escaping, no `dangerouslySetInnerHTML`), product image URLs must be `https://`, and the API accepts no token from query strings. |

## Data integrity

* Prices and totals are computed server-side from the Products table; client prices are rejected.
* All writes use parameterised DynamoDB expressions (placeholders for every name and value).
* Stock writes are conditional (`available >= q`, `reserved >= q`) — never negative.
* Order state changes are conditional on the expected source state and `version`.
* Idempotency keys (per customer) prevent duplicate orders; deterministic ids prevent duplicate payments/notifications.

## Infrastructure

| Area | Control |
|---|---|
| IAM | `use_lab_role = false`: one role per function, only the actions/resources it needs (e.g. the Stock Lambda can update Orders and Inventory and publish to one topic; it cannot read Users or Payments). `use_lab_role = true` (Academy) uses the broad LabRole — a documented lab limitation. |
| Encryption at rest | DynamoDB (AWS-owned keys), SQS (SSE-SQS), SNS order/customer topics (`alias/aws/sns`), S3 (SSE-S3). The alerts topic is unencrypted because CloudWatch cannot publish to topics using the AWS-managed key; it carries alarm metadata only. |
| Encryption in transit | API Gateway is HTTPS-only; queue and topic policies deny non-TLS access; CloudFront option redirects to HTTPS. The default S3 website endpoint is HTTP-only (diagram choice) — use `enable_cloudfront = true` outside the lab. |
| Queue access | Work queues accept messages only from the order-events topic (`aws:SourceArn`); each DLQ accepts redrive only from its own queue. |
| CORS | Only the deployed frontend origin plus `cors_allowed_origins` (default `http://localhost:5173`); never `*`. |
| Throttling | Stage default 20 rps / burst 40 (configurable). There is no per-account lockout; the PBKDF2 cost and stage throttling slow password guessing (add WAF for more). |
| Logs | Structured JSON with correlation and order ids; keys containing password/token/authorization/secret/card are redacted; request bodies and Authorization headers are never logged; retention 7 days. |
| Errors | Internal exceptions return a generic 500 with a correlation id — no stack traces or messages. |
| Secrets | None in code or frontend. The only secret is `JWT_SECRET`, generated by Terraform (so it is in Terraform state) and set only on the Auth and Authorizer functions; other Lambda env vars hold only names/ARNs/flags. Terraform state, `.env*`, `terraform.tfvars` are git-ignored. |
| Payments | Simulated; no card data is requested, transmitted or stored. |
| Test hooks | Product `testBehavior` can only be set by admins and is ignored unless `enable_test_scenarios = true`; it is hidden from customers. |
| Replays | No public endpoint replays queue messages; DLQ redrive is admin-only, and stale events are ignored by attempt number. |

## Known gaps / production hardening

* Learner Lab's `LabRole` is far broader than least privilege.
* Add AWS WAF (rate-based rules) in front of the API/CloudFront, and MFA for admins.
* Use a customer managed KMS key for SNS/SQS/DynamoDB if key-level audit is required.
* Add a Content-Security-Policy via CloudFront response headers policy.
* No email verification, password reset or account lockout (no Cognito) — add them, or move the JWT key to Secrets Manager with rotation, before production.
* Access tokens cannot be revoked before they expire (1 h; authorizer cache 5 min). Rotating `random_password.jwt_secret` signs everyone out.
