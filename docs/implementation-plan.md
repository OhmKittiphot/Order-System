## 2. Environment constraints found

| Constraint | Impact | Decision |
|---|---|---|
| AWS Academy Learner Lab cannot create IAM roles/policies | Least-privilege per-Lambda roles cannot be created in the lab | `use_lab_role = true` (default) attaches the pre-existing `LabRole`. `use_lab_role = false` creates one least-privilege role per Lambda (for a normal account). Both paths are in Terraform. |
| Lab credentials are temporary and sessions stop | State must survive; resources keep costing while the session is stopped | Local Terraform state by default; cleanup scripts; no always-on resources |
| Lab may block some services | CloudFront / email may be restricted | CloudFront optional (`enable_cloudfront`), no managed identity service (users live in DynamoDB, no email verification), customer email via SNS optional |
| This build sandbox has no access to pypi / npm / HashiCorp | Cannot install boto3, moto, Vite, React Router or Terraform here | Data access goes through a thin gateway so the business logic is unit-tested with an in-memory DynamoDB fake that evaluates real condition/update expressions. Terraform is checked with a static reference checker; `terraform validate`/`plan` must be run by the user. |

## 3. Architecture decisions

1. **Authentication** – as in the diagram, without Cognito. The *Auth Lambda* (`POST /auth/register`, `POST /auth/login`, `POST /auth/refresh`) stores the profile and a PBKDF2 password hash in the Users table and issues HS256 JWTs (access 1 h, refresh 1 day) signed with a key generated by Terraform. The **Lambda Authorizer** (HTTP API `REQUEST` authorizer) verifies signature, issuer, token type and expiry before every protected route and passes `userId`/`role` to the target Lambda. Role (`customer` / `admin`) is stored on the user profile and enforced again in every admin handler (403).
2. **Reliable publishing** – the order item is written with `outboxStatus = PENDING_PUBLISH` in the same DynamoDB transaction as the idempotency record. The Order Lambda then publishes `OrderPlaced` and removes the marker. If publishing fails, a scheduled **outbox publisher Lambda** (every minute) queries the sparse `outbox-index` and republishes. Consumers are idempotent, so a duplicate publish is harmless.
3. **Event flow** – one SNS topic (`order-events`, the diagram's "OrderPlaced topic") carries all order lifecycle events. SQS subscriptions use **SNS filter policies on the `eventType` message attribute** and **raw message delivery**:
   - stock-queue ← `OrderPlaced`
   - payment-queue ← `InventoryReserved`
   - notify-queue ← `OrderConfirmed`, `OrderFailed`
   This keeps the diagram's fan-out shape but guarantees payment only runs after stock is reserved.
4. **Atomic stock reservation** – one `TransactWriteItems` decrements `available` / increments `reserved` for every line (condition `available >= qty`) *and* moves the order `PENDING → PROCESSING`. All lines reserve or none do; no partial reservations.
5. **Payment** – simulated. One transaction writes the payment record (condition: not exists), moves the order to `CONFIRMED` (or `FAILED`) and either commits or **releases** the reservation (compensation) in the same transaction.
6. **Concurrency** – every order update is conditional on the expected current state *and* on `version`; late events carry the order `attempt` number and are ignored when stale.
7. **Notifications** – Notify Lambda records each notification in the Notifications table with a deterministic id (conditional put = dedupe), optionally publishes to the customer-email SNS topic (filter policy per customer), and sets `notificationStatus`. "SNS accepted" is never reported as "delivered".
8. **Retry** – `POST /admin/orders/{id}/retry` with a classification of failure types (business / transient-stuck / DLQ / permanent) and an optimistic-lock + cooldown to block duplicate retries. DLQ redrive via `POST /admin/dlq/{queue}/redrive` (SQS `StartMessageMoveTask`).
9. **Packaging** – Lambda code only uses the Python standard library + boto3 (bundled in the runtime), so one zip built by Terraform `archive_file` serves all functions with different handlers. No layers needed.
10. **Money** – integer minor units (`priceMinor`, `totalMinor`) to avoid floating point; currency configurable (default `THB`).

## 4. DynamoDB access patterns (summary – see `database-design.md`)

| # | Access pattern | Table / index | Operation |
|---|---|---|---|
| 1 | Get order by id | Orders (PK `orderId`) | GetItem |
| 2 | Customer order history, newest first | Orders `customer-index` (`customerId`, `createdAt`) | Query |
| 3 | All orders for admin, newest first | Orders `entity-index` (`entityType`, `createdAt`) | Query |
| 4 | Orders by status | Orders `status-index` (`status`, `createdAt`) | Query |
| 5 | Orders waiting to be published | Orders `outbox-index` (sparse `outboxStatus`, `createdAt`) | Query |
| 6 | Active products for catalog | Products `catalog-index` (`catalogStatus`, `name`) | Query |
| 7 | Stock for products | Inventory (PK `productId`) | BatchGetItem / GetItem |
| 8 | Payment attempts of an order | Payments (PK `orderId`, SK `attempt`) | Query / conditional Put |
| 9 | Customer notifications | Notifications (PK `customerId`, SK `notificationId`) | Query |
| 10 | Idempotent order creation | Idempotency (PK `idempotencyId`, TTL) | conditional Put in transaction |
| 11 | User profile | Users (PK `userId`) | Get / Put |

## 5. Order state machine (summary – see `order-workflow.md`)

```
PENDING --InventoryReserved--> PROCESSING --PaymentSucceeded--> CONFIRMED (terminal)
PENDING --OutOfStock--> FAILED            PROCESSING --PaymentDeclined--> FAILED (stock released)
PENDING|PROCESSING --admin cancel--> CANCELLED (terminal, stock released if reserved)
FAILED (retryable) --admin retry--> PENDING
```
